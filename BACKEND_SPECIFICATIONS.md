# Backend Specifications - ESG CRM

## Overview

REST API backend for the ESG CRM module. The backend handles data storage, validation, and CRUD operations. The frontend manages code generation (project codes) and catalog values (free-form strings).

---

## Database Tables

### 1. `clients` - Client/Prospect Registry

| Field               | Type         | Nullable | Description                           |
| ------------------- | ------------ | -------- | ------------------------------------- |
| `id`                | UUID / INT   | NO (PK)  | Auto-generated primary key            |
| `name`              | VARCHAR(255) | NO       | Company name (razón social)           |
| `nit`               | VARCHAR(50)  | NO       | Tax identification number             |
| `code`              | VARCHAR(20)  | YES      | Project code generated by frontend    |
| `organization_type` | VARCHAR(255) | YES      | Type of organization (free text)      |
| `norm`              | VARCHAR(255) | YES      | Applicable standard/norm (free text)  |
| `city` | VARCHAR(100) | YES | City |
| `department` | VARCHAR(100) | YES | Department/State |
| `address` | VARCHAR(255) | YES | Physical address |
| `phone` | VARCHAR(50) | YES | Main company phone |
| `email` | VARCHAR(255) | YES | Main company email |
| `website` | VARCHAR(255) | YES | Company website URL |
| `is_active`         | BOOLEAN      | NO       | Default: true. Active/inactive status |
| `is_prospect`       | BOOLEAN      | NO       | Default: false. Client vs Prospect    |
| `observations`      | TEXT         | YES      | General notes                         |
| `show_resources` | BOOLEAN | NO | Default: false. Toggle to show/hide resources |
| `contacts` | JSON | YES | Array of contact objects |
| `resources` | JSON | YES | Array of resource/image objects |
| `created_at` | TIMESTAMP | NO | Creation timestamp |
| `updated_at`        | TIMESTAMP    | NO       | Last update timestamp                 |

**`contacts` JSON Structure:**

```json
[
  {
    "name": "string",
    "position": "string",
    "phone": "string",
    "email": "string",
    "isPrimary": false
  }
]
```

**`resources` JSON Structure:**

```json
[
  {
    "name": "string",
    "url": "string",
    "type": "image | document",
    "uploadedAt": "2025-01-01T00:00:00Z"
  }
]
```

## Entity Relationship Diagram

```
┌─────────────┐       ┌─────────────────┐
│   clients   │       │    projects     │
├─────────────┤       ├─────────────────┤
│ id (PK)     │──1:N──│ id (PK)         │
│ name        │       │ client_id (FK)  │
│ nit         │       │ code            │
│ is_active   │       │ status          │
│ is_prospect │       │ responsible     │
│ contacts*   │       │ services*       │
│ resources*  │       │ start_date      │
│ ...         │       │ end_date        │
└─────────────┘       └────────┬────────┘
                               │
                    ┌──────────┼──────────┐
                    │          │          │
               ┌────▼───┐ ┌───▼────┐ ┌───▼────┐
               │ quotes │ │ events │ │documents│
               ├────────┤ ├────────┤ ├────────┤
               │ id(PK) │ │ id(PK) │ │ id(PK) │
               │client_ │ │entity_ │ │entity_ │
               │  id(FK)│ │ type   │ │ type   │
               │project_│ │entity_ │ │entity_ │
               │  id(FK)│ │  id    │ │  id    │
               │ status │ │ type   │ │ name   │
               │ ...    │ │ ...    │ │ ...    │
               └────────┘ └────────┘ └────────┘

               ┌──────────┐
               │ tenders  │
               ├──────────┤
               │ id (PK)  │
               │ status   │
               │ ...      │
               └──────────┘
```

**Notes:**

- `*` = JSON fields stored directly in the table
- `events` and `documents` use polymorphic associations via `entity_type` + `entity_id`
- No separate catalog tables - all type/status fields are free-text strings managed by frontend

## API Endpoints

### Clients

```
GET    /api/clients              # List clients (with filters: is_active, is_prospect, search)
GET    /api/clients/:id          # Get client by ID
POST   /api/clients              # Create client
PUT    /api/clients/:id          # Update client
DELETE /api/clients/:id          # Delete client (soft delete recommended)
```

### Projects

```
GET    /api/projects             # List projects (with filters: client_id, status, search)
GET    /api/projects/:id         # Get project by ID (include client data)
POST   /api/projects             # Create project (frontend sends code + services)
PUT    /api/projects/:id         # Update project (including services)
DELETE /api/projects/:id         # Delete project
```

### Quotes

```
GET    /api/quotes               # List quotes (with filters: client_id, project_id, status)
GET    /api/quotes/:id           # Get quote by ID
POST   /api/quotes               # Create quote
PUT    /api/quotes/:id           # Update quote
DELETE /api/quotes/:id           # Delete quote
```

### Tenders

```
GET    /api/tenders              # List tenders (with filters: status, type, search)
GET    /api/tenders/:id          # Get tender by ID
POST   /api/tenders              # Create tender
PUT    /api/tenders/:id          # Update tender
DELETE /api/tenders/:id          # Delete tender
```

### Events

```
GET    /api/events                    # List events (filters: entity_type, entity_id)
POST   /api/events                    # Create event
DELETE /api/events/:id                # Delete event
```

### Documents

```
GET    /api/documents                 # List documents (filters: entity_type, entity_id)
POST   /api/documents                 # Create document record
DELETE /api/documents/:id             # Delete document
POST   /api/documents/upload          # Upload file (multipart/form-data)
```

## Database Constraints

### Foreign Keys

- `projects.client_id` → `clients.id`
- `quotes.client_id` → `clients.id`
- `quotes.project_id` → `projects.id`

### Indexes

```sql
-- Clients
CREATE INDEX idx_clients_is_active ON clients(is_active);
CREATE INDEX idx_clients_is_prospect ON clients(is_prospect);
CREATE INDEX idx_clients_nit ON clients(nit);
CREATE INDEX idx_clients_name ON clients(name);

-- Projects
CREATE INDEX idx_projects_client_id ON projects(client_id);
CREATE INDEX idx_projects_status ON projects(status);
CREATE INDEX idx_projects_code ON projects(code);

-- Quotes
CREATE INDEX idx_quotes_client_id ON quotes(client_id);
CREATE INDEX idx_quotes_project_id ON quotes(project_id);
CREATE INDEX idx_quotes_status ON quotes(status);

-- Tenders
CREATE INDEX idx_tenders_status ON tenders(status);
CREATE INDEX idx_tenders_type ON tenders(type);

-- Events (polymorphic)
CREATE INDEX idx_events_entity ON events(entity_type, entity_id);
CREATE INDEX idx_events_date ON events(date);

-- Documents (polymorphic)
CREATE INDEX idx_documents_entity ON documents(entity_type, entity_id);
```

## Business Rules

1. **Project Code Generation**: Frontend generates the code (format: `{consecutive}-{abbreviation}`) and sends it in the POST/PUT request. Backend stores it as-is.

2. **Client vs Prospect**: Distinguished by `is_prospect` boolean field. Both share the same table.

3. **Active/Inactive**: The `is_active` field controls visibility. Soft delete recommended (set `is_active = false` instead of deleting).

4. **Polymorphic Associations**: Events and Documents can belong to any entity (client, project, quote, tender) using `entity_type` + `entity_id`.

5. **JSON Fields**: `contacts`, `resources`, and `services` are stored as JSON. Backend should validate the JSON structure on save.

6. **All Type/Status Fields are Free Text**: No catalog tables needed. Frontend manages all dropdown values and sends them as strings.
